# 安全设计说明

> 金枢 FinTrust Agent · 面向银行业务的可信 AI 智能体系统

本项目的核心命题不是「让 AI 更聪明」，而是**让 AI 在金融场景下值得被信任**。
本文档说明系统如何保证：模型可以自由理解与表达，但**永远无法越权**。

---

## 1. 威胁建模

| 编号 | 威胁 | 影响 | 应对措施 |
| --- | --- | --- | --- |
| T1 | 模型幻觉导致越权转账 | 严重 | 权限引擎独立于模型，服务端强制校验 |
| T2 | 提示词注入（用户诱导模型放宽限制） | 严重 | 模型输出不参与权限判定；仅作为参数候选 |
| T3 | 前端绕过 UI 直接调用 API | 严重 | 所有权限判定在服务端执行，与前端无关 |
| T4 | 请求重放 / 重复提交导致重复扣款 | 高 | `Idempotency-Key` + 工单状态机 |
| T5 | 模型服务不可用导致核心业务瘫痪 | 高 | 本地规则引擎降级 + 熔断器 |
| T6 | 密钥泄漏到前端 | 高 | 密钥仅存后端环境变量，从不下发 |
| T7 | 敏感操作无留痕，无法追责 | 高 | 五种处置全量只追加审计 |
| T8 | 金额计算浮点误差 | 中 | 全链路整数分存储与计算 |
| T9 | 演示环境被误认为真实交易 | 中 | 全量 `is_simulated` 标记 + 界面显式声明 |

## 2. 核心原则

### 原则一：模型是感知器，不是决策者

```
┌─────────────────────────────────────────────────────────────┐
│  模型输出（可被攻击、可能幻觉）                              │
│    intent / slots / reply                                    │
└──────────────────────┬──────────────────────────────────────┘
                       │  仅作为「参数候选」向下传递
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  策略引擎（确定性规则，不含任何模型成分）                    │
│    输入：amount_cents, daily_total_cents, is_frequent_payee, │
│          is_new_payee, target_is_self, remark_sensitive     │
│    输出：level(green|yellow|red) + decision + 可解释 rules   │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
              服务端执行闸门
```

`PolicyEngine.evaluate()` 的**函数签名中不存在**「模型建议的权限」这类参数。
这不是约定，而是类型层面的约束 —— 模型即使在返回 JSON 里写 `"risk": "green"`，也不会被读取。

### 原则二：默认拒绝

- 动作类型不在白名单 → 直接 `block`
- 日累计超过红线 → 直接 `block`
- 任何无法解析的入参 → 422 / 400，绝不"猜一个默认值然后放行"

### 原则三：前端不是安全边界

前端会隐藏不该点的按钮，但**这只是体验优化**。真正的强制点在服务端：

```bash
# 直接绕过前端调用 API（不传 confirm）
curl -X POST http://127.0.0.1:8000/api/v1/transfers/execute \
  -H "Content-Type: application/json" \
  -d '{"order_no":"TR2026...","confirm":false}'
# → HTTP 409 {"error":{"code":"CONFIRMATION_REQUIRED", ...}}
```

## 3. 三级权限模型

### 3.1 阈值（可通过环境变量调整）

| 配置项 | 默认值 | 含义 |
| --- | --- | --- |
| `POLICY_YELLOW_SINGLE_MAX` | ¥5,000 | 单笔超过此值 → 黄色 |
| `POLICY_RED_SINGLE_MIN` | ¥50,000 | 单笔达到此值 → 红色 |
| `POLICY_YELLOW_DAILY_MAX` | ¥20,000 | 当日累计超过此值 → 升级红色 |
| `POLICY_RED_DAILY_TOTAL` | ¥100,000 | 当日累计超过此值 → 直接阻断 |

### 3.2 判定顺序

策略引擎按**固定顺序**执行规则，先命中者生效，但**后续规则只会继续抬高等级**（不会降级）：

```
Rule 0  白名单检查        非白名单动作 → block
Rule 1  强制 MFA 动作     挂失 → red + MFA
Rule 2  金额定级
        ├ 单笔 ≥ 红线阈值          → red
        ├ 单笔 > 黄色上限           → yellow
        └ 否则                      → green
Rule 3  当日累计
        ├ 累计 + 本笔 > 总红线      → block（不可撤销）
        ├ 累计 + 本笔 > 黄色日上限   → red（MFA）
        ├ 累计 + 本笔 > 单笔黄上限   → yellow
Rule 4  收款人风险
        ├ 首次转账                  → 至少 yellow
        └ 非常用联系人              → 至少 yellow
Rule 5  自转账                     → 至少 yellow
Rule 6  备注敏感词                 → red（MFA）
Rule 7  单笔硬上限                 → block
```

### 3.3 等级对应的服务端行为

| 等级 | 服务端行为 | HTTP | 前端表现 |
| --- | --- | --- | --- |
| 🟢 green | 直接执行，落库流水 + 写审计 | `200` | 一键"立即执行" |
| 🟡 yellow | **拒绝执行**，返回明细等待确认 | `409` | 展示明细 + "我已核对，确认执行" |
| 🔴 red | **拒绝执行**，下发 MFA 挑战 | `428` | 6 位验证码输入框（演示模式直接显示） |
| ⛔ blocked | **永久拒绝**该工单 | `403` | 展示拦截原因与命中规则 |

### 3.4 可解释性

每一次判定都会产出 `rules: string[]`，逐条说明命中了哪条规则：

```json
{
  "level": "red",
  "reason": "单笔金额 88000.00 元达到大额阈值 50000.00 元。",
  "rules": [
    "单笔金额 ≥ 50000.00 元 → 红色",
    "收款人为常用联系人"
  ]
}
```

这条链路同时用于：前端展示 → 审计日志 → 用户申诉时的举证材料。

## 4. 幂等控制

### 4.1 机制

- 写操作（转账 / 虚拟卡 / 挂失）必须携带 `Idempotency-Key`（前端自动生成 `web-<ts>-<rand>`）
- 服务端以 `(key, endpoint)` 唯一约束落库 `idempotency_records`
- 首次请求：写入 `in_progress` 记录 → 执行 → 写入 `done` + 响应体
- 重复请求：
  - 同键同参 + `done` → **返回首次结果**，不再执行
  - 同键同参 + `in_progress` → `409 IDEMPOTENCY_IN_PROGRESS`
  - 同键异参 → `409 IDEMPOTENCY_CONFLICT`
- 执行失败 → 删除 `in_progress` 记录，允许用户重试

### 4.2 双层保险

即使幂等键被绕过，**工单状态机**仍能兜底：

```python
if order.status == "executed":
    # 直接返回首次执行结果，绝不二次扣款
    return {...}
```

实测：同一幂等键重复提交，`balance_after` 与 `transaction_id` 完全一致。

## 5. 多因子身份验证（模拟）

| 属性 | 实现 |
| --- | --- |
| 挑战生成 | 6 位随机数字，`mfa_{random}` |
| 有效期 | 300 秒 |
| 最大尝试 | 5 次，超限锁定 |
| 一次性 | 校验通过即 `consumed = True`，不可复用 |
| 挑战绑定 | `challenge_id` 持久化在 `transfer_orders.mfa_challenge_id` |
| 演示下发 | 演示模式由后端在响应中返回 `demo_code`（真实场景应走短信 / 推送，绝不放在响应里） |

**关键修复记录**：早期版本在重试验证码时未读取工单上持久化的 `challenge_id`，
导致第二次校验时重新发起了挑战、用户输入的验证码始终不匹配。已通过工单字段修复并补充测试。

## 6. 异常熔断与降级

```
circuit_breaker = CircuitBreaker("llm", threshold=5, reset_timeout=60)
```

| 状态 | 触发条件 | 行为 |
| --- | --- | --- |
| `closed` | 正常 | 请求直通 |
| `open` | 连续失败 ≥ 5 次 | 抛 `CircuitOpenError`，Agent 降级到本地规则引擎 |
| `half_open` | 熔断后经过 60s | 放行一次探测请求，成功则回到 `closed` |

**降级不是失败**：熔断打开时，意图识别、参数抽取、任务规划、工具调用全部照常工作，
只是不再调用外部模型。核心业务闭环在任何网络状况下都保持可用。

熔断状态通过 `GET /api/v1/agent/capabilities` 对外暴露，可实时观测。

## 7. 密钥与数据隔离

| 要求 | 实现 |
| --- | --- |
| API Key 不入前端 | `LLM_API_KEY` 只从后端 `.env` / 环境变量读取，`app/core/config.py` 持有 |
| 响应体不含密钥 | `/health`、`/agent/capabilities` 只返回 `llm_configured: bool` 与模型名 |
| 前端无 .env 密钥 | `frontend/` 只有可选的 `VITE_API_BASE_URL`（公开地址，非密钥） |
| 账号脱敏 | API 只返回 `masked_account_no` / `masked_card_no` |
| `.env` 不入库 | `.gitignore` 已排除 `.env`、`*.db`、`node_modules`、`.venv` |

## 8. 审计日志

### 8.1 五种处置全覆盖

| 处置 | 动作示例 | decision |
| --- | --- | --- |
| 放行 | 只读查询、常规转账执行 | `allow` |
| 需确认 | 转账预览命中黄色规则 | `confirm` |
| 需验证 | 红色操作触发 MFA | `mfa` |
| 拦截 | 余额不足、日累计超红线、验证码错误 | `block` |
| 流程留痕 | Agent 对话 | `allow` |

### 8.2 日志字段

`id · actor · action · target_type · target_id · risk_level · decision · reason · detail_json · ip_address · is_simulation · created_at`

`detail_json` 保存完整上下文（金额、命中规则、当日累计、挑战 ID 等），可支撑事后追溯。

### 8.3 只追加

`audit_logs` 仅由 `security/audit.py` 的 `write_audit_log()` 写入，
业务代码不提供任何更新 / 删除接口。前端「安全审计中心」提供按权限等级筛选与统计。

## 9. 模拟环境声明

| 位置 | 声明形式 |
| --- | --- |
| 数据库 | 每条 `transactions` 带 `is_simulated=true`；每条 `audit_logs` 带 `is_simulation=true` |
| API | 账户总览返回 `simulation_notice`；转账结果返回 `simulation_notice` |
| 前端 | 顶部全局提示条；侧边栏底部常驻声明；流水行内「模拟交易」标记；虚拟卡「模拟操作，不具备真实支付能力」 |
| 银行卡 | 挂失提示「模拟操作，不会影响任何真实卡片」 |

**绝不伪造交易成功。** 每一次成功都真实完成了：策略判定 → 余额校验 → 扣款 → 落库流水 → 写审计。
失败场景（余额不足 / 累计超限 / 验证码错误 / 未确认）均返回明确错误码。

## 11. 生产环境演进方向（当前未实现，供说明）

本项目为竞赛 MVP，以下为真实落地时必须补齐的部分：

1. **真实 MFA 通道**：短信 / 邮件 / TOTP 推送，验证码绝不通过 HTTP 响应下发
2. **身份认证**：接入 OAuth2 / OIDC，用户身份来自令牌而非固定 `demo-user`
3. **密钥托管**：改用 Vault / KMS 管理模型密钥，支持轮换
4. **数据库**：迁移到 PostgreSQL + 读写分离，审计日志进入独立不可变存储（WORM）
5. **风控扩展**：接入真实反欺诈模型与名单服务，策略引擎支持规则热更新
6. **传输与存储加密**：TLS 强制、敏感字段落库加密、密钥轮换
7. **速率限制**：按用户 / IP 限流，防止接口被刷
8. **资金通道隔离**：对接持牌机构的沙箱环境，永远与生产资金系统物理隔离
